# 产品决策复盘模板

> 用一个具体取舍积累工作思维。本模板为空白，不代表任何决策已获批准；只填写有依据的过程，未知内容保留待确认。

## 记录身份与依据

| 字段 | 待填写内容 |
| --- | --- |
| 稳定案例编号 / 标题 | 分配新编号，不与既有案例重复 |
| 决策日期 / 整理日期 | 分别记录；不知道时写未核实 |
| 参与者 / 决策负责人 | 区分提出、讨论和最终确认，不能仅凭在场判定全员同意 |
| 适用范围 / 版本 | 当时的目标、约束及版本 |
| 记录状态 | 历史资料整理 / 待当事人确认 / 已确认，择一 |
| 原始依据 | 文档、会议或聊天导出的相对路径和章节；没有存档时注明原话与上下文及证据限制 |
| 相关主题 / 需求 / 问题 | 稳定编号及链接 |

## 1. 当时为什么要做决定

- 什么用户问题、业务目标或已有矛盾触发这次讨论？
- 有什么事实或证据？哪些只是当时的假设？
- 当时有哪些时间、资源、技术和设计约束？

## 2. 考虑过哪些方案

| 方案 | 用户或业务收益 | 代价和限制 | 当时支持或放弃它的理由 | 依据 |
| --- | --- | --- | --- | --- |
| 待填写 | 待填写 | 待填写 | 不补造未讨论过的方案 | 待填写 |

## 3. 最终如何选择

- 最终方案、确认人及确认依据：待填写。
- 选择时最看重什么：待填写，并区分当事人原话与整理者归纳。
- 哪些东西因此被放弃或推迟：待填写。
- 哪些条件改变后应重新讨论：待填写。
- 哪些问题还没决定：待填写，链接到待确认清单。

## 4. 从案例中学到了什么

| 层次 | 内容 | 确认状态 |
| --- | --- | --- |
| 当时的具体决定 | 只写资料支持的结论 | 待填写 |
| 当事人的明确偏好 | 需本人表达，注明适用对象 | 没有则写未提供 |
| 整理者观察 | 对判断方式的归纳，附证据及可能反例 | 默认待确认 |
| 团队共同原则 | 明确谁、何时确认及适用条件 | 未确认前不能从上行自动升级 |

用条件化语言归纳，例如“在某类场景与约束下，优先检查什么”。不要从一次取舍推导成“团队总是怎样”，也不要把个人偏好泛化为团队约束。

## 5. 后续结果与适用限制

| 项目 | 记录 |
| --- | --- |
| 希望改善的结果 | 待填写 |
| 后续验证方式与依据 | 未实际验证时明确写未验证 |
| 实际结果 / 观察日期 | 未观察时保留未知 |
| 是否出现反例或副作用 | 待填写 |
| 是否修订原则或业务规则 | 附新记录和替代范围 |

决策记录可以保留当时判断，不能据此声称方案已经实现、上线或成功。

## 6. 确认与知识更新

- 确认人、日期、确认范围：待填写。
- 需要修改的业务主题及适用版本：待填写。
- 是否纳入 [产品思维与工作方式](../wiki/团队协作/产品思维与工作方式.md)：个人偏好 / 待确认观察 / 已确认团队原则，择一并说明依据。
- 是否产生需求变化：若是，关联 [需求与逻辑审查模板](需求与逻辑审查模板.md)，继续走讨论与审核流程。
- 更新目录、问题清单和维护日志，并检查来源和链接。
