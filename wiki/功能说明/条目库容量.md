# 条目库容量

> FEAT-006｜整理：2026-11-10｜需求：资料整理待审核，公式有冲突｜实现 / 上线：未核实｜审核人 / 时间：尚无。
> 依据：Epic 7 PRD·US-24·1.3、US-27·6、US-28·2.2及附录一。

## 容量怎么算

**资料无法给出没有歧义的最终公式。**

| 位置 | 表达 |
| --- | --- |
| US-24·1.3 | 暂定可创建榜单上限 5 个，5×55=275；随允许创建上限动态调整，不能写死 275 |
| 同文附录及较早概览 | “用户榜单数×55”，该处未明确已建数量还是允许上限 |

55 来自 5 个评级等级×每级最多 11 条。但两种基数不同；若按已建数量为 0 计算，新用户独立建条目如何成立？是否有最低容量、删除榜单是否缩容也受影响，见 [Q-002](../../questions/待确认事项.md#q-002-条目库容量公式的基数不一致)。

## 不同操作达到容量时怎么办

| 场景 | PRD 行为 |
| --- | --- |
| 文件夹或添加入口中新建 | 弹窗拦截，提示先删除条目释放空间 |
| 榜单内半屏弹窗中新建 | 新建区域替换为容量提示，不显示表单，不再另弹拦截弹窗 |
| 待复制总数不超过剩余容量 | 显示全选 |
| 待复制总数超过剩余容量 | 隐藏全选，显示剩余可添加数；勾选后递减，达上限则其他未选项置灰 |

这是交互要求，并非并发条件下后端校验已完成的证明。容量颜色等视觉参数另查设计和原文 US-24，不在这里补写。

## 为什么采用动态容量

6.24 评审希望容量与榜单能力匹配，避免榜单能添加而库已满，并支持后续扩容。理由能解释目标，不能消除基数歧义。
