## 一、P0-1 口令码

> **背景**：分享时自动复制口令码，用户粘贴到小红书/抖音/社群即可。口令码用表情符号包装规避平台限流。小程序内新增搜索入口识别口令码跳转。这是 Phase 2 增长破圈的核心通道。

| 决策维度 | 问题 | 推荐方案 | 理由 | 最终决定 |
| --- | --- | --- | --- | --- |
| 口令码格式 | 纯数字 vs 字母数字混合 vs emoji组合？ | 6位数字+前后emoji装饰，如 🎵123456🎵 | 纯数字易记易输入；emoji作为视觉锚点和防屏蔽包装；6位支持百万级榜单足够 | 用“用户名（取前6位字）+的品味+随机字母两位”这种形式，因为要最大程度规避平台违规限流处罚，注意边界情况就行 |
| 口令码与榜单映射 | 一个榜单固定一个口令码，还是可以生成多个？ | 一个榜单一个永久口令码，榜单创建时自动生成 | 简化用户心智；永久码方便反复传播；不需要「生成新口令」的额外操作 | 一个榜单一个口令 |
| 口令码有效期 | 永久有效 vs 有时效（如7天）？ | 永久有效 | 榜单本身是长周期内容；熟人社交场景下用户可能过一段时间才看到；失效会导致跳转失败体验差 | 永久 |
| 分享触发时机 | 哪些分享场景触发自动复制口令码？ | 点击「分享」按钮 → 分享卡弹窗出现时，同时自动复制口令码到剪贴板，toast提示「口令码已复制」 | 06-17会议结论：不做独立「选择口令码」流程，分享即复制；用户粘贴即可，零额外操作 | 不，和“微信分享给朋友”、“保存位图片”平级，加一个按钮叫“复制榜单口令码”，点击后toast提示「口令码已复制」 |
| 小程序内搜索入口 | 口令码在哪里粘贴搜索？位置和交互形式？ | 首页顶部加搜索框（🔍图标），点击展开输入框，粘贴口令码回车搜索。同时支持从微信剪贴板自动识别（小程序启动时检测剪贴板是否有Taste口令码） | 搜索框是通用能力入口（未来可扩展搜索榜单/用户）；自动识别剪贴板降低手动粘贴摩擦 | ok，但是那个自动检测剪贴板要调研一下微信小程序官方有没有开发接口或者需要用户签什么协议 |
| 口令码展示样式 | 在分享卡、分享文案中口令码如何呈现？ | 分享卡底部独立一行：emoji + 「搜索口令」+ 口令码；分享文案模板：「我的\[Taste]榜单来啦！🔍搜索口令 🎵123456🎵 在小程序里找到我」 | 和分享卡视觉风格一致；提供完整可复制文案模板降低运营成本 | 分享卡不用写，然后这个文案模版有限流违规风险，所以就不做了 |
| 口令码识别后的跳转 | 用户输入口令码后跳转到哪里？ | 直接跳转到对应榜单的查看详情页（view-list），底部显示「创建我的版本」CTA按钮 | 先让用户看到内容，再看是否转化；和现有的分享链接进入体验一致 | ok |
| 内容审核策略 | 口令码分享出去的榜单需要内容审核吗？ | Phase 2 暂不做内容审核，后续视数据决定是否加举报入口 | 06-18业务会议确认：信任熟人社交自净能力；加审核会拖慢分享实时性 | ok |
| 口令码数据追踪 | 需要埋点追踪哪些数据？ | ①口令码生成次数 ②口令码被搜索次数（区分手动输入/剪贴板自动识别）③通过口令码进入榜单的UV ④从口令码到创建榜单的转化率 | 衡量外部分发效果的核心漏斗；为运营策略提供数据支撑 | 这个现在先别管 |

## 二、P0-2 条目库 + 批量复制

> **背景**：条目库是 Phase 2 最核心的架构级功能。核心理念——同一条目可以在多个榜单复用，可以从他人榜单取条目到自己的库。条目库 = 「我的榜单」页面下新增条目Tab。批量复制 = 查看他人榜单时多选条目加入自己的库。这个功能覆盖了「一键复制榜单」的场景（全选=复制整个榜单）。

| 决策维度 | 问题 | 推荐方案 | 理由 | 最终决定 |
| --- | --- | --- | --- | --- |
| 条目库入口 | 条目库放在哪里？ | 在首页「我的榜单」页面加顶部Tab切换：「榜单」（现有列表）｜「条目库」（新增，展示所有个人条目） | 06-17会议结论；和现有页面结构内聚，不新增独立页面 | 应该会在主页加一个底部的tab，作为条目库的入口，不过具体的交互形式还没定 |
| 数据独立性 | 从他人榜单复制条目到自己的库，是「拷贝一份」还是「引用原条目」？ | 拷贝一份——复制时创建独立的条目副本，后续各自修改互不影响 | ①如果原条目被删除，引用会出问题；②用户可能想修改复制来的条目（换图、改简介），拷贝更灵活；③去重和容量控制更简单 | ok |
| 条目库展示方式 | 条目库Tab内如何展示条目？ | 网格布局展示条目卡片（缩略图+名称），支持按添加时间倒序；顶部搜索框支持按名称搜索 | 条目数量多时需要搜索；缩略图网格空间效率高于列表 | ok |
| 从他人榜单复制的触发 | 查看他人榜单时，如何进入「批量复制条目」模式？ | 在查看态榜单详情页（view-list），右上角加「···」菜单，其中一项为「复制条目到我的库」。点击后进入多选模式：每个条目卡片出现勾选框，底部出现操作栏（全选｜取消｜加入条目库(已选N)） | 参考06-17会议中程豫对批量复制交互的描述；用户不是每次看榜单都要复制，所以放在二级菜单不干扰正常浏览 | ok |
| 批量选择后的目标 | 选中的条目加入条目库后，是否同时提示「创建新榜单」？ | 入库后弹出轻提示：「已加入条目库，共N条。是否立即创建新榜单？」→ 点击跳转创建榜单页，并自动勾选刚加入的条目 | 降低操作路径：用户复制条目大概率是为了创建榜单；不强制，让用户选择 | 不，只toast提示，不承载按钮交互，因为这个地方有很多种情况，用户不想创建新的-这个提示打断用户体验；用户想选一个已经创建过的榜单加-后续跳转比较复杂不适合在这里做源头；用户已达到榜单数量上限-又得打回，感觉前后矛盾，所以不加 |
| 创建榜单时调用条目库 | 创建/编辑榜单添加条目时，如何从条目库选取？ | 在现有的「添加条目」半屏弹窗中，增加一个Tab：「新建条目」｜「从条目库选择」。选「从条目库」时展示条目库内容，支持多选勾选，确认后批量加入当前榜单 | 保持创建流程不变，加一个Tab降低认知成本；多选批量添加效率高 | 把原来的那个方形的“添加”按钮变成上下两个按钮，一个是新建，一个是从库添加，这样更高效 |
| 去重逻辑 | 如果用户尝试复制一个自己库里已有的条目（同名），如何处理？ | 轻提示：「该条目已在你条目库中」，仍允许复制（创建副本），但提示用户 | 不强制阻止（用户可能就是想建两个版本）；但提示避免无意识重复 | ok |
| 容量限制 | 条目库有上限吗？ | 上限100条，达到80条时提醒 | 和小程序轻量定位一致；V1.0榜单上限5个，条目库100条在合理范围；后续视使用数据调整 | 80也不用提醒 |
| 条目库中的编辑 | 在条目库中能否编辑条目？ | 可以编辑基础信息（名称、图片、简介），但修改不影响已添加到榜单中的该条目副本 | 保持数据独立性；用户可能想完善条目信息后再用于新榜单 | 可以 |
| 条目库删除 | 删除条目库中的条目，是否影响已用到榜单中的副本？ | 不影响——删除只移出条目库，已在榜单中的条目保留 | 数据独立性原则；用户删的是「模板」不是「使用中的实例」 | ok |

条目部分关键核心问题是：条目既然可复制可复用，复制复用后的条目又可以被修改编辑，那是否只是为了简化操作，作为一个模板使用，而做不到复制或复用的子条目和母条目保持链接并具有同一原子化的属性，比如之后可能会做问答，那条目可能会具有点赞量，榜单级别，被复用数等等指标

## 三、P1-1 榜单点赞

> **背景**：06-18业务会议确认缩小范围——从「条目点赞」调整为「榜单点赞」，业务判断条目太细。点赞需显示头像+名称（非纯数字），增强熟人社交激励感。Glitter提议探索贴纸墙等轻量互动形式。只做点赞不做点踩（分享是正向行为）。

| 决策维度 | 问题 | 推荐方案 | 理由 | 最终决定 |
| --- | --- | --- | --- | --- |
| 点赞入口位置 | 在哪里操作点赞？ | 榜单详情页（查看态view-list）底部，和现有的「查看次数」并排，加一个❤️点赞按钮 | 查看榜单时自然产生点赞冲动；和查看次数信息层级一致 | ok，我会把交互做的更有趣一点 |
| 点赞反馈 | 点击点赞后即时反馈是什么？ | ❤️按钮填充变红 + 数字+1 + 轻触觉反馈（微信小程序haptic） | 三重反馈强化满足感；触觉反馈是微信小程序能力，提升交互质感 | 差不多 |
| 点赞人展示 | 在榜单上如何展示谁点了赞？ | 点赞按钮旁边显示点赞人头像行（最多显示5个头像+名称），超出显示「+N人」；点击头像行展开完整点赞人列表（按点赞时间倒序） | 头像+名称是06-18业务会议Glitter明确要求；前5个预览保持页面简洁，展开满足好奇心 | 最表层只显示头像（头像叠放+显示“n人表示很赞”）然后点击这个头像区域，出现半屏弹窗，可以在内部上下滑动查看所有点赞人的头像和昵称 |
| 贴纸墙（是否做） | Phase 2是否做贴纸墙？ | Phase 2先做基础点赞（头像+名称），贴纸墙作为P1.5——基础点赞上线后观察使用数据，如果点赞率低再开发贴纸墙增强趣味性 | Glitter提议值得探索，但贴纸墙涉及贴纸管理后台、前端交互复杂度高；先验证基础点赞是否满足需求 | 对 |
| 贴纸墙方案（如需做） | 如果做贴纸墙，具体交互是？ | 点赞后弹出贴纸选择器（预设6-8个贴纸：🌶️🔥💯👑🎯✨💎），选择一个贴纸贴在榜单封面上。榜单上展示贴纸集合（类似B站「硬币」的趣味表达） | 预设贴纸避免审核风险；贴纸比干巴巴点赞更有表达力；贴纸集合视觉效果好 | ok |
| 点赞者身份 | 谁可以点赞？ | 登录用户都可以点赞（不限制必须和创建者有微信好友关系） | 保持开放；不做好友关系链，和PRD的「不做社区」定位一致 | ok |
| 取消点赞 | 是否可以取消点赞？ | 可以——再次点击❤️取消，头像行即时移除 | 用户可能误操作；取消应该是轻量操作 | ok |
| 点赞通知 | 是否需要通知榜单创建者？ | Phase 2暂不做主动推送通知。在创建者的「我的榜单」列表卡片上显示点赞数即可 | 小程序推送能力有限；推送多了反而骚扰；点赞数在首页卡片可见满足「被看见」的正向反馈需求 | 不通知 |
| 查看者可见信息 | 查看者看到榜单点赞信息吗？ | 看到完整信息——点赞数+头像行+点击展开完整列表 | 公开数据增强社交信任；看到熟人点赞可促进二次传播 | 都可以看到，这个是公开的 |

## 四、P1-2 收藏/历史记录

> **背景**：06-18会议Glitter强烈主张收藏功能（「看到喜欢的榜单就想收藏」），06-17会议程豫认为收藏+历史应合并为一个统一页面，保持小程序精简。历史记录和收藏心理模型不同（被动记录 vs 主动保存），交互方案需权衡。

| 决策维度 | 问题 | 推荐方案 | 理由 | 最终决定 |
| --- | --- | --- | --- | --- |
| 收藏与历史是否合并 | 一个统一页面 vs 两个独立页面？ | 合并为一个「浏览记录」页面，内分两个Tab：「收藏」｜「历史」。历史自动记录最近50条浏览；收藏由用户手动操作 | 程豫底线：不新增两个独立页面；Tab方式既有区分又不膨胀页面数 | 行 |
| 收藏入口 | 在哪里可以收藏榜单？ | 榜单详情页（view-list）右上角「···」菜单中增加「收藏」选项；收藏后图标变为★实心 | 和复制条目同级入口；收藏是低频操作，放二级菜单合理 | ok |
| 浏览记录入口 | 从哪里进入「浏览记录」页面？ | 首页（我的榜单页）顶部右侧加📋图标入口，点击进入「浏览记录」页面 | 首页是个人中心，自然入口；图标不占空间 | 反正是首页的某个tab进去，具体位置未定 |
| 收藏数量限制 | 收藏有上限吗？ | 上限50条，达到上限提示「收藏已满，请清理后再添加」 | 工具型小程序克制；50条满足核心用户需求 | ok |
| 置顶功能 | 是否支持收藏置顶？ | 支持——收藏列表左滑出现「置顶」操作，置顶后卡片变横向小圆圈展示在收藏Tab顶部（最多3个） | 06-17会议程豫提出的交互方案；微信小程序下拉历史已有此模式验证 | 不用 |
| 历史记录范围 | 历史记录记录什么？ | 记录用户查看过的所有他人榜单（按时间倒序），去重（同一榜单多次查看只保留最新一次） | 帮助用户找回「之前看过但没收藏」的榜单（Glitter场景） | ok |
| 历史记录自动清理 | 历史记录需要自动清理吗？ | 保留最近50条，超出自动淘汰最旧记录。用户可手动清空全部历史 | 和微信小程序下拉历史逻辑一致；50条覆盖几周使用量 | ok |
| 创建者视角 | 我自己的榜单出现在收藏/历史里吗？ | 不出现——收藏和历史只针对他人榜单 | 自己的榜单已在首页列表，无需重复 | ok |

## 五、P1-3 POI 地点标记

> **背景**：06-17会议程豫新增——条目标记地理位置（POI），为Phase 3智能问答打基础。业务理解这是基础设施投资。场景：创建「北京昌平最好吃的20家餐厅」时，给每个条目标记具体地址。Phase 3可以根据POI自动聚合推荐。

| 决策维度 | 问题 | 推荐方案 | 理由 | 最终决定 |
| --- | --- | --- | --- | --- |
| POI绑定粒度 | POI绑定在条目上还是榜单上？ | 条目级——每个条目可绑定一个POI地点 | ①一个榜单里的条目可能分布在不同地点（如「北京美食榜」涵盖全城）；②条目级数据更精准，Phase 3智能推荐才能按条目维度聚合；③榜单级地点过于粗糙 | |
| 地点选择方式 | 用户如何为条目标记地点？ | 在「添加条目」半屏弹窗新增「📍添加地点」字段（选填）。点击后：①顶部搜索框输入地名搜索（调用微信地图API）②下方地图选点（可拖动定位pin）③「使用当前位置」快捷按钮 | 三种方式覆盖不同场景：搜索最常用、地图选点精确、当前位置快捷；参考小红书POI选择交互 | |
| POI是否必填 | POI标记是选填还是必填？ | 选填——不强制 | ①不是所有条目都有明确地点（如「最喜欢的Kpop专辑」）；②强制填会打断创建流程，降低创建率；③靠「无地点条目无法参与Phase 3推荐」来自然激励 | |
| POI数据存储 | 存什么信息？ | \{ poiName, address, latitude, longitude, poiId(微信地图POI ID) } | 存POI ID方便后续查询和聚合；经纬度支撑地图展示；名称和地址用于前端展示 | |
| POI在条目卡片上的展示 | 条目卡片上如何展示POI信息？ | 在条目卡片底部加一行小字：📍地点名称（灰色小字，不超过一行），点击可跳转微信地图查看 | 信息层级低于条目名称和图片；不喧宾夺主；点击跳转提供实用价值 | |
| POI对他人可见 | 查看他人榜单时能看到POI吗？ | 能看到——创建者标记了POI的条目展示📍地点名称 | POI是公开信息，增强榜单信息量和可信度；也为Phase 3推荐做数据储备 | |
| API免费额度 | 微信地图API是否有免费额度？ | 待多多确认。如额度不足考虑：①限每人每天N次POI搜索 ②使用腾讯地图WebService API（免费额度更高） | 06-17会议待办项；影响交互方案中搜索次数上限 | |

## 六、P1-4 复制追踪

> **背景**：06-17会议新增——创作者可以看到自己的榜单/条目被多少人复制、衍生出多少新榜单。06-18业务会议明确透明度策略：聚合数据可见，不暴露具体谁复制。和点赞同理，是正向反馈机制。

| 决策维度 | 问题 | 推荐方案 | 理由 | 最终决定 |
| --- | --- | --- | --- | --- |
| 追踪粒度 | 追踪「复制榜单」还是「复制条目」？ | 追踪两个维度——榜单被复制次数 + 条目被复制次数，在各自位置展示 | ①06-18会议侧重榜单级追踪；②条目库功能做起来后，条目级追踪也有价值；③两者数据独立展示不冲突 | |
| 聚合展示规则 | 展示什么信息？ | 榜单编辑页/首页榜单卡片：显示「被复制 N 次 · 衍生 M 个新榜单」。条目不单独展示复制次数 | 06-18会议结论：聚合数据可见，不暴露具体谁；衍生=有人基于这个榜单的条目创建了新榜单 | |
| 「衍生」的定义 | 什么算「衍生」？ | 定义：用户B复制了用户A榜单中≥2个条目，并用这些条目创建了新榜单 → 算1次衍生 | ≥2个条目才能体现「A的榜单影响了B的创作」；单条目复用太常见不构成「衍生」 | |
| 展示位置（创作者视角） | 创作者在哪里看到复制追踪数据？ | 首页榜单列表：每个榜单卡片底部显示「👁 N次查看 · ❤️ N赞 · 📋 被复制N次」。点击榜单卡片进入编辑页后，顶部显示更详细数据（衍生数） | 首页卡片提供概览；编辑页提供更详细数据（创作者关心） | |
| 查看者是否看到 | 查看他人榜单时能看到复制追踪数据吗？ | 看到「被复制N次」（和点赞数处理一致），不显示衍生数 | 复制数=社会证明信号，增强榜单吸引力；衍生数偏创作者向，查看者不需要 | |
| 数据更新频率 | 复制追踪数据实时更新还是定期更新？ | 实时更新——每当发生复制行为立即更新计数 | 数据量小（熟人社交），实时没有性能压力 | |

## 一、P0-1 口令码 — 最终方案

**口令码格式**：`来看[用户名前6字]的[形容词]品味[aB]`

- 形容词池（随机取1个）：高雅 / 超绝 / 独到 / 封神 / 神仙

- 随机字母（2位）：a-z，大小写敏感，26×26=676种

- 总组合：5×676=3,380种，公域防遍历

- 用户名变化时：生成时固化，旧口令不失效

- 纯emoji昵称：过滤emoji取汉字/字母，都没有则用"用户"

| 决策维度 | 最终决定 | 关键原因 |
| --- | --- | --- |
| 口令码格式 | 来看\[用户名前6字]的\[形容词]品味\[aB] | 全自然语言，零导流特征，规避限流 |
| 口令码与榜单映射 | 一个榜单一个口令，创建时自动生成 | 简化心智 |
| 有效期 | 永久有效 | 榜单长周期内容 |
| 分享触发 | 独立按钮「复制榜单口令码」，与微信分享/保存图片平级；toast提示成功/失败；不关联分享卡 | 用户显式操作，口令码和分享卡解耦 |
| 搜索入口 | 首页顶部搜索框（🔍），粘贴搜索。自动检测剪贴板需先调研微信API | 通用入口 |
| 口令码展示 | 分享卡不写口令码；不提供文案模板 | 规避外部分发限流风险 |
| 识别后跳转 | 跳转查看详情页（view-list），底部「创建我的版本」CTA | 先看再转化 |
| 内容审核 | Phase 2 不做 | 信任熟人自净 |
| 数据追踪 | Phase 2 暂不做 | 先上线 |
